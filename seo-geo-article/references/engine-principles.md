# Движок блога: принципы и приёмочные проверки

Это не код для копирования, а спецификация. Стек любой (Node, Python, Go, Astro, Hugo,
Eleventy, самописный скрипт), дизайн свой. Движок готов, когда выполняются проверки в конце.
Главная идея: всё, что можно забыть руками, проверяет сборка и **падает**, а не предупреждает.

## 1. Вывод: статический HTML, почти без JS

- Каждая страница – готовый HTML: текст, ссылки, шапка видны без выполнения скриптов. Боты
  ИИ-поиска часто не исполняют JS.
- CSS встроен или один файл; шрифты свои (WOFF2), без CDN во время работы.
- JS – маленький отложенный файл для мелочей (переключатель темы, копировать ссылку, цель
  клика CTA). Он никогда не переписывает ссылки и не дорисовывает контент.
- Светлая и тёмная темы, тема применяется до первой отрисовки (без вспышки).

## 2. Контент: Markdown/MDX с frontmatter, один slug = один файл

`content/<slug>.mdx`, имя файла = `slug`. Схема frontmatter:

```yaml
slug: statistika-rils              # = имя файла, латиница, дефисы
title: "статистика рилс 2026: какие показатели сравнивать"   # H1
description: "1–2 предложения, прямой ответ"                  # лид и meta description
summary: "что читатель получит"
type: article                      # article (проза) | guide (с командами и кодом)
tags: [ ... ]
author: "<публичный автор>"
published: true                    # false = черновик, в сборку не попадает
published_at: 2026-11-10T09:00:00Z
updated_at: 2026-11-10T09:00:00Z   # >= published_at, двигается только с правкой текста
last_verified_at: 2026-11-10T08:00:00Z
verified_sources: [ https://... ]
proofs: [ "что видимо доказывает статья" ]
target_query: "статистика рилс"
headline_formula: "Предмет"
hook_formula: "Данные и выбор"
cover_alt: "описание сцены обложки"
```

Валидируй схему при сборке (Zod, JSON Schema, pydantic – что угодно). Неизвестное или
пропущенное обязательное поле – ошибка сборки.

## 3. Гейты сборки (каждый валит сборку)

| Гейт | Что проверяет |
|---|---|
| Контент-линт | лид до первого `##`, длина текста, FAQ, «Проверено на…», автор, даты, нет плейсхолдеров, нет блоков кода в `article`, пересечение с другими статьями (`SKILL.md`, раздел про проверку) |
| SEO-шапка | на каждой странице ровно один `<title>`, описательный («тема: суть – Бренд», после удаления имени бренда остаётся смысл; рекомендуемый минимум 30 знаков), уникальный по сайту; ровно один `<link rel="canonical">`, абсолютный https, на своём домене, равный собственному URL страницы (форма со слэшем), не «/» для внутренней страницы; непустой `meta description` |
| Внутренние ссылки | каждая ссылка на свой домен в HTML (`href`, `src`, `srcset`, `poster`), в `.md`-двойниках и `llms*.txt` ведёт на существующий маршрут или файл вывода; ошибка печатает «страница → цель» |
| Локальные ассеты | каждая картинка, шрифт, файл, на которые ссылается страница, есть в выводе |
| Утечки | в выводе нет черновиков (`published: false`), плейсхолдеров, секретов (`token`, `secret`, `password`, ключи), путей с диска, чужих брендов при white-label |
| Манифест сборки | `build-manifest.json`: бренд, домен, список маршрутов, каждый файл с sha256; лишний или подложенный файл = ошибка. Без меток времени: одинаковый вход = одинаковые байты |
| Блоки графиков | валидный JSON, известный тип, совпадающие длины рядов; ошибка с именем slug |

Те же функции проверки SEO-шапки используются и после деплоя на живом сайте – правила
одни.

## 4. Картинки

- Из одного исходника – AVIF, WebP, JPEG нескольких ширин (рекомендуемо 800 и 1600).
- Никогда не растягивать: ширина производной не больше исходника.
- `<picture>` с `<source type="image/avif">`, `<source type="image/webp">`, `<img>` JPEG;
  у `<img>` всегда `width` и `height` – сдвиг вёрстки (CLS) 0.
- `loading="lazy"` и `decoding="async"` для всего ниже первого экрана; обложка статьи – без
  lazy.
- Бюджет размера на производную (например, 250 КБ) – превышение = ошибка сборки.
- Кеш кодирования по sha256 исходника и настройкам кодека: повторная сборка не перекодирует.
- Производные в отдельном пространстве путей (`_img/...`), чтобы не затереть исходник.

## 5. GEO-выходы

- `llms.txt` – название, одна строка о сайте, список статей со ссылками на `.md`.
- `llms-full.txt` – полный текст всех статей в Markdown (графики – таблицами).
- `.md`-двойник каждой статьи (`/guides/<slug>.md`) + `<link rel="alternate" type="text/markdown">`.
- `sitemap.xml` – только канонические URL, `lastmod` из даты последней правки контента
  (например, из git), а не из времени сборки.
- `robots.txt` – явная политика по поисковым и обучающим ботам, ссылка на sitemap.
- JSON-LD: `Article`/`TechArticle` (заголовок, автор, даты, картинка), `BreadcrumbList`,
  `FAQPage` – только если на странице есть видимый FAQ, `Organization` с растровым логотипом.
- Open Graph и Twitter: `og:title`, `og:description`, `og:url` = canonical, `og:image`
  1200×675 с размерами и alt, `twitter:card=summary_large_image`, `og:locale`.

## 6. Деплой

1. Сборка и все гейты зелёные.
2. **Бэкап** текущего прода (архив веб-корня или снапшот). Бэкап не удался – деплоя нет.
3. Сухой прогон синхронизации: если загрузка удалит файлы с прода, которых нет в сборке
   (сборка со старой ветки), – стоп, пока удаление не подтверждено.
4. **Атомарная выкладка**: загрузить в новую папку и переключить симлинк, либо rsync с
   проверкой контрольных сумм. Никогда не править файлы на сервере руками.
5. Сброс кеша CDN, если он есть.
6. Сигналы поисковикам (не валят деплой, но их результат печатается): IndexNow для Яндекса
   и Bing по изменённым URL, отправка sitemap в Google Search Console через API или вручную.
7. **Проверка на проде**: обойти sitemap и проверить SEO-шапку каждой страницы теми же
   правилами, что в сборке; ненулевой код выхода при любой ошибке.
8. **Скриншоты матрицы браузера**: 5 ширин (например, 360, 390, 768, 1280, 1920) × светлая и
   тёмная темы, страница целиком. Смотреть глазами: переносы посреди слова, наезды,
   обрезанные обложки, горизонтальный скролл. Любой headless-браузер.

## 7. Аналитика

- Счётчик подключается из конфига и только если указан ID; без ID – ни одного скрипта.
- Цели: клик по CTA, дочитывание (скролл до конца или видимость последнего раздела).
- UTM-метки на CTA собираются при сборке, а не скриптом.
- Search Console и Вебмастер подключены, sitemap отправлен – это основной источник данных
  о показах по запросам.

## Движок готов, если…

- [ ] Страница статьи открывается с выключенным JS и содержит весь текст, ссылки и шапку.
- [ ] Один slug = один файл; slug ≠ имя файла валит сборку.
- [ ] Черновик (`published: false`) не попадает ни в HTML, ни в sitemap, ни в `llms*.txt`.
- [ ] Удали canonical у одной страницы – сборка падает и называет страницу.
- [ ] Сделай два одинаковых title – сборка падает.
- [ ] Добавь ссылку на несуществующую статью или без слэша – сборка падает с «страница → цель».
- [ ] Удали картинку, на которую ссылается статья, – сборка падает.
- [ ] Положи в контент строку `<<PLACEHOLDER` или `api_key=` – сборка падает.
- [ ] Каждая картинка в `<picture>` с AVIF/WebP/JPEG, `width`/`height`; CLS 0 в Lighthouse.
- [ ] Есть `llms.txt`, `llms-full.txt`, `.md`-двойник каждой статьи, `sitemap.xml`, `robots.txt`.
- [ ] JSON-LD проходит валидатор schema.org; `FAQPage` только при видимом FAQ.
- [ ] OG-превью корректно в мессенджере (картинка, заголовок, описание).
- [ ] Деплой делает бэкап, сухой прогон удалений и атомарную выкладку.
- [ ] После деплоя проверка шапки на проде проходит, IndexNow и sitemap отправлены.
- [ ] Скриншоты 5 ширин × 2 темы просмотрены, дефектов нет.
- [ ] Повторная сборка без изменений даёт тот же манифест.
